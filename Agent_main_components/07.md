# Oracle AI Vector Search Workflow

## 1. Big Picture

Oracle AI Vector Search provides a workflow for turning raw data such as PDFs and documents into **semantic search results**.

The overall pipeline is:

```text
Raw Data
   ↓
Extract Text
   ↓
Chunk Text
   ↓
Generate Embeddings
   ↓
Store Vectors
   ↓
Create Vector Index
   ↓
Similarity Search
   ↓
Relevant Chunks
   ↓
LLM
   ↓
RAG Answer
```

The lesson describes **5 primary steps**:

1. Generate embeddings
2. Store vectors in Oracle tables
3. Create vector indexes
4. Run similarity queries
5. Use results for RAG

---

# 2. Step 1 — Generate Embeddings

An embedding converts data such as text into a numerical vector.

For example:

```text
"Python is a programming language"
                ↓
        Embedding Model
                ↓
[0.21, -0.45, 0.87, 0.13, ...]
```

The resulting vector represents the **semantic meaning** of the text.

Oracle supports two major approaches for generating embeddings.

### Approach 1 — In-database embeddings

The embedding model runs inside the Oracle Database.

```text
Text
 ↓
ONNX Model
 ↓
Embedding
 ↓
Vector
```

Oracle uses **ONNX Runtime** for this.

### Approach 2 — External embeddings

The database calls an external embedding API.

```text
Oracle Database
      ↓
 REST API
      ↓
OpenAI / Cohere / Other Provider
      ↓
Embedding
      ↓
Oracle Database
```

---

# 3. What is ONNX?

**ONNX = Open Neural Network Exchange**

ONNX is an open format for representing machine-learning models.

The important idea here is:

```text
ML Model
   ↓
ONNX format
   ↓
Can potentially run inside Oracle
```

Oracle can use supported ONNX models with its runtime to generate embeddings inside the database.

### Why is in-database embedding useful?

Because the data does not have to leave the database to reach an external embedding service.

Conceptually:

```text
Database
┌───────────────────────────┐
│ Document                  │
│     ↓                     │
│ ONNX Embedding Model      │
│     ↓                     │
│ Vector                    │
└───────────────────────────┘
```

Potential benefits:

* No external network call
* Lower network latency
* Data can remain inside the database environment
* Useful for privacy/security-sensitive workloads

However, you are limited to models/runtime configurations supported by the database environment.

---

# 4. External Embedding APIs

The other approach is to call an external provider.

Examples mentioned in the lesson:

* OpenAI
* Cohere
* Other embedding providers

Conceptually:

```text
Oracle
  ↓
REST API
  ↓
Embedding Provider
  ↓
Embedding Vector
  ↓
Oracle
```

### Why use external models?

You may want access to newer or more powerful embedding models that aren't running inside the database.

So there is a basic trade-off:

| In-database                            | External API                 |
| -------------------------------------- | ---------------------------- |
| Model runs inside DB                   | Model runs outside DB        |
| No external embedding network call     | Network call required        |
| Data can stay within DB environment    | Data may be sent to provider |
| Limited to supported models            | More model choices           |
| Convenient for controlled environments | Access to provider ecosystem |

# 5. Step 2 — Store Vectors

Once an embedding is generated, Oracle stores it in a table using the **VECTOR data type**.

For example:

```sql
CREATE TABLE documents (
    id NUMBER,
    text_content VARCHAR2(4000),
    embedding VECTOR
);
```

Conceptually:

| ID | Text                             | Embedding            |
| -- | -------------------------------- | -------------------- |
| 1  | Dogs are loyal animals           | `[0.21, -0.44, ...]` |
| 2  | Cats are independent animals     | `[0.18, -0.31, ...]` |
| 3  | Python is a programming language | `[0.72, 0.12, ...]`  |

The important part is that the vector can live **alongside normal business data**.

For example:

```text
Customer ID
Customer Name
Order ID
Product
Price
Document Text
Embedding Vector
```

This is one of the major ideas behind Oracle AI Vector Search:

> **Vector data can live alongside traditional relational data.**

# 6. Oracle VECTOR Data Type

Oracle provides a native `VECTOR` data type.

The simplest declaration is:

```sql
embedding VECTOR
```

This gives a flexible vector column.

You can also specify stricter requirements.

Conceptually:

```sql
embedding VECTOR(768, INT8)
```

This means:

* Exactly **768 dimensions**
* Stored using **INT8**

So:

```text
VECTOR
```

means flexible.

Whereas:

```text
VECTOR(768, INT8)
```

means:

```text
Exactly 768 dimensions
+
INT8 storage format
```

# 7. Vector Dimensions

Suppose an embedding model produces:

```text
[0.2, 0.5, -0.1, 0.8]
```

This vector has:

```text
4 dimensions
```

Another model could produce:

```text
[0.2, 0.5, -0.1, 0.8, 0.3, ...]
```

with hundreds or thousands of dimensions.

The important rule is:

> **A vector produced by a particular embedding model has a specific dimensionality.**

For example:

```text
Embedding model
      ↓
768-dimensional vector
```

Every embedding generated by that model normally has the same dimensionality.

# 8. Vector Storage Formats

The lesson mentions four storage formats:

### 1. FLOAT32

32-bit floating-point values.

Example:

```text
[0.1234, -0.8721, 0.4412]
```

### 2. FLOAT64

64-bit floating-point values.

Provides greater numerical precision but generally requires more storage than FLOAT32.

### 3. INT8

8-bit integer representation.

Uses less storage than floating-point representations, subject to the model/representation requirements.

### 4. Binary

A binary representation.

Useful for certain specialized vector representations.

---

# 9. Dense vs Sparse Vectors

This is an important concept.

## Dense Vector

Every dimension is stored.

Example:

```text
[0.2, 0.0, 0.7, 0.0, 0.4]
```

Even the zero values are represented.

```text
dimension 1 → 0.2
dimension 2 → 0.0
dimension 3 → 0.7
dimension 4 → 0.0
dimension 5 → 0.4
```

---

## Sparse Vector

Only the non-zero dimensions need to be represented.

For:

```text
[0.2, 0.0, 0.7, 0.0, 0.4]
```

we could conceptually represent only:

```text
dimension 1 → 0.2
dimension 3 → 0.7
dimension 5 → 0.4
```

Sparse storage can be useful for embedding models whose vectors contain many zeros.

### Remember

```text
Dense  → store every dimension
Sparse → store non-zero dimensions
```

# 10. Step 3 — Create Vector Indexes

Now imagine we have:

```text
10 vectors
```

Searching all of them isn't a big problem.

But imagine:

```text
10 million vectors
```

If we compare a query vector against every vector:

```text
Query
 ↓
Vector 1
Vector 2
Vector 3
Vector 4
...
Vector 10,000,000
```

That can become expensive and slow.

This is why we use **vector indexes**.

The basic idea:

> **An index helps the database find likely similar vectors without scanning every vector.**

---

# 11. No Index vs Vector Index

### Without an index

```text
Query
 ↓
Compare against every vector
 ↓
Find nearest vectors
```

This is essentially a full scan.

### With an index

```text
Query
 ↓
Vector Index
 ↓
Search promising regions
 ↓
Nearest vectors
```

Much more scalable for large collections.

---

# 12. HNSW Index

**HNSW = Hierarchical Navigable Small World**

The transcript calls it a hierarchical network small world index.

HNSW is a graph-based approximate nearest-neighbor search structure.

The basic mental model:

```text
Vector A ─── Vector B
   │            │
   │            │
Vector C ─── Vector D
```

Vectors are represented as nodes in a graph.

Nodes connect to nearby/related nodes.

HNSW has multiple layers.

Conceptually:

```text
Top Layer
A ───────── D
 \          /
  \        /

Middle Layer
A ── B ── D ── E

Bottom Layer
A ─ B ─ C ─ D ─ E ─ F ─ G ─ H
```

The upper layers are smaller and allow fast navigation.

The lower layers contain more detail.

### Mental model

Think of Google Maps:

```text
Country level
    ↓
City level
    ↓
Street level
```

You don't examine every street in the entire country.

You progressively move toward the relevant area.

Similarly, HNSW navigates through graph layers toward vectors that are likely to be similar.

### HNSW key idea

> **Graph-based + hierarchical + fast approximate search**

---

# 13. IVF Index

**IVF = Inverted File**

The transcript describes IVF as a partition-based approach.

The vectors are grouped into clusters.

K-means can be used to create those clusters.

Example:

```text
10,000 vectors

        ↓ clustering

Cluster 1
[Vector A, B, C...]

Cluster 2
[Vector D, E, F...]

Cluster 3
[Vector G, H, I...]

...
```

Suppose a query is closest to Cluster 2.

Instead of searching every cluster:

```text
Cluster 1 ❌
Cluster 2 ✅
Cluster 3 ❌
Cluster 4 ❌
...
```

the system can focus on the most relevant partitions.

### Mental model

Imagine a library:

```text
All books
   ↓
Science
Technology
History
Mathematics
Biology
```

If you're searching for a biology book, you don't inspect every book in every section.

You first identify the relevant section.

### IVF key idea

> **Cluster vectors → identify relevant clusters → search those clusters**

---

# 14. HNSW vs IVF

| Feature         | HNSW                    | IVF                                 |
| --------------- | ----------------------- | ----------------------------------- |
| Basic idea      | Graph                   | Clusters/partitions                 |
| Structure       | Multi-layer graph       | Vector clusters                     |
| Search strategy | Navigate graph          | Search relevant partitions          |
| Main concept    | Neighbor connections    | Cluster selection                   |
| Useful for      | Fast approximate search | Large collections with partitioning |

Don't worry about implementing these algorithms yet.

At this stage, remember:

```text
HNSW → graph

IVF → clusters
```

# 16. Step 4 — Similarity Search

After storing and indexing vectors, we can search them.

Suppose the user asks:

```text
"Which documents discuss dogs?"
```

First:

```text
User Query
    ↓
Embedding Model
    ↓
Query Vector
```

Then Oracle compares the query vector against stored vectors.

```text
Query Vector
      ↓
Vector Distance
      ↓
Document 1 → distance 0.12
Document 2 → distance 0.81
Document 3 → distance 0.23
Document 4 → distance 0.05
```

Smaller distance means greater similarity for the distance-based metrics being used here.

Therefore:

```text
Document 4 → 0.05  ← most similar
Document 1 → 0.12
Document 3 → 0.23
Document 2 → 0.81
```

---

# 17. VECTOR_DISTANCE

Oracle provides a vector distance function:

```text
VECTOR_DISTANCE(vector1, vector2, metric)
```

Conceptually:

```text
VECTOR_DISTANCE(
    document_embedding,
    query_embedding,
    COSINE
)
```

It returns a distance value.

Then you can sort by that distance:

```sql
ORDER BY VECTOR_DISTANCE(
    embedding,
    :query_embedding,
    COSINE
)
```

and retrieve the first few results.

For example:

```sql
SELECT *
FROM documents
ORDER BY VECTOR_DISTANCE(
    embedding,
    :query_embedding,
    COSINE
)
FETCH FIRST 5 ROWS ONLY;
```

This means:

> Find the 5 documents whose vectors are closest to the query vector.

---

# 18. Combining Vector Search with Normal SQL

One of the powerful ideas here is that vector search can be combined with ordinary SQL filters.

Example:

```sql
SELECT *
FROM houses
WHERE city = 'New York'
  AND price < 500000
ORDER BY VECTOR_DISTANCE(
    image_embedding,
    :query_embedding
)
FETCH FIRST 10 ROWS ONLY;
```

This can mean:

> Find houses in New York under $500,000 that are visually/semantically most similar to this query.

So we can combine:

```text
Traditional SQL filtering
+
Vector similarity
```

# 19. Distance Metrics

The lesson introduces four important metrics.

## 1. Cosine Distance

Very commonly used for text embeddings.

It focuses on the **angle/direction** between vectors.

Conceptually:

```text
       A
      /
     /
    / θ
   /
  B
```

The angle between the vectors matters.

### Mental model

```text
Cosine → direction / angle
```

For many text embedding use cases, cosine similarity/distance is a common choice.

---

# 20. Euclidean Distance

Also called **L2 distance** in many contexts.

It measures straight-line distance between vectors.

In 2D:

```text
A ●
   \
    \
     \
      ● B
```

The length of the line between A and B is the Euclidean distance.

Formula:

```text
√((x₂-x₁)² + (y₂-y₁)²)
```

For higher-dimensional vectors, the same idea extends across all dimensions.

### Mental model

```text
Euclidean → straight-line distance
```

---

# 21. Dot Product / Inner Product

Dot product compares vectors using their components.

For two vectors:

```text
A = [a1, a2, a3]

B = [b1, b2, b3]
```

Dot product:

```text
A · B
=
a1b1 + a2b2 + a3b3
```

It considers both:

* direction
* magnitude

### Mental model

```text
Dot Product → direction + magnitude
```

Be careful with interpretation: depending on the exact similarity/distance convention, ranking may use larger similarity or transformed distance values. Follow the metric expected by the database/model.

---

# 22. Manhattan Distance

Manhattan distance sums absolute differences.

For two vectors:

```text
A = [1, 5]
B = [4, 9]
```

Distance:

```text
|1-4| + |5-9|

= 3 + 4

= 7
```

### Mental model

Imagine walking through city blocks rather than flying diagonally.

```text
A ────┐
      │
      │
      └──── B
```

That's why it is called Manhattan distance.

### Formula

```text
|x₁-x₂| + |y₁-y₂| + ...
```

---

# 23. Distance Metric Summary

| Metric         | Mental Model                | Common Use                      |
| -------------- | --------------------------- | ------------------------------- |
| Cosine         | Angle/direction             | Text embeddings                 |
| Euclidean / L2 | Straight-line distance      | Spatial/geometric data          |
| Dot Product    | Direction + magnitude       | Some embedding/retrieval setups |
| Manhattan      | Sum of absolute differences | Certain sparse/robust settings  |

### Easy memory trick

```text
Cosine    → Angle
Euclidean → Straight line
Dot       → Multiply + add
Manhattan → Block-by-block distance
```

---

# 24. Why the Same Distance Metric Matters

A very important point from the lesson:

> **Use the distance/similarity metric appropriate to the embedding model and its documented recommendations.**

For example, if the model documentation recommends cosine similarity, use the corresponding cosine-based search metric.

Don't randomly switch metrics just because another metric exists.

The embedding model and retrieval metric should be treated as a compatible pair.

# 25. Step 5 — RAG

After similarity search, we have relevant chunks.

Those chunks can be provided to an LLM.

This is:

**RAG = Retrieval-Augmented Generation**

The basic pipeline:

```text
User Question
      ↓
Query Embedding
      ↓
Vector Search
      ↓
Relevant Chunks
      ↓
LLM
      ↓
Answer
```

Example:

User:

```text
What is Oracle AI Vector Search?
```

Vector search finds:

```text
Chunk 1 → definition
Chunk 2 → architecture
Chunk 3 → vector indexes
```

Those chunks are placed into the LLM's context.

The LLM then generates an answer using the retrieved information.

# 27. Chunking

Chunking is extremely important in RAG.

Suppose we have:

```text
100-page PDF
```

We don't normally send the entire PDF as one giant piece to an embedding model.

Why?

Because embedding models have input/token limits.

So we divide it:

```text
100-page PDF
      ↓
Chunk 1
Chunk 2
Chunk 3
Chunk 4
...
Chunk N
```

Each chunk gets its own embedding.

```text
Chunk 1 → Vector 1
Chunk 2 → Vector 2
Chunk 3 → Vector 3
...
```

Then the vector database can retrieve individual relevant chunks.

# 29. Chunk Size

Chunk size controls how much information goes into each chunk.

Example:

```text
Chunk size = 500 tokens
```

could produce:

```text
Chunk 1 → tokens 1–500
Chunk 2 → tokens 501–1000
Chunk 3 → tokens 1001–1500
```

If chunks are too small:

```text
❌ Context may be lost
```

If chunks are too large:

```text
❌ Retrieval may become less precise
❌ More context may be sent to the LLM
```

So chunk size matters.

# 30. Chunk Overlap

Suppose we split text like this:

```text
Chunk 1:
A B C D E F

Chunk 2:
G H I J K L
```

There is no overlap.

But we can create:

```text
Chunk 1:
A B C D E F

Chunk 2:
E F G H I J

Chunk 3:
I J K L M N
```

Here:

```text
E F
```

is shared between Chunk 1 and Chunk 2.

And:

```text
I J
```

is shared between Chunk 2 and Chunk 3.

This is called **chunk overlap**.

### Why overlap?

Because important meaning can cross chunk boundaries.

For example:

```text
Chunk 1:
The company's revenue increased significantly because...

Chunk 2:
...the new AI product launched successfully.
```

Without overlap, the relationship between those sentences can become harder to retrieve.

Overlap helps preserve contextual continuity.

# 39. What You Should NOT Confuse

### Vector ≠ Embedding Model

```text
Embedding model → creates embedding
Embedding → numerical representation
Vector → numerical structure storing that representation
```

### HNSW ≠ Embedding

HNSW is an **index/search structure**.

It doesn't create embeddings.

```text
Embedding Model → Vector
Vector → HNSW Index
```

### IVF ≠ RAG

IVF is a **vector index**.

RAG is an **application architecture**.

```text
IVF → helps retrieve vectors efficiently

RAG → retrieves information and gives it to an LLM
```

### Chunking ≠ Embedding

```text
Chunking → divides document
Embedding → converts each chunk into numbers
```
